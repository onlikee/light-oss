# 后端架构整改计划

- 状态：代码整改完成，目标共享卷验收待完成
- 更新时间：2026-08-24
- 适用范围：`backend/`
- 剩余验收：在目标 RWX 共享卷上以两个独立后端实例复验跨节点可见性、原子 rename 与故障接管。

## 1. 背景

当前后端是一个 Go + Gin + GORM 的分层单体，已经具备清晰的 `handler -> service -> repository/storage` 依赖方向，也对上传、覆盖、删除、回收站和站点发布实现了数据库事务与文件补偿。现有架构适合轻量私有部署，但写入性能、横向扩展能力和运行时治理已经成为继续扩展的主要约束。

本计划以性能和可扩展性为第一优先级，同时处理会直接影响扩容安全的限流、数据库连接、迁移和文件清理问题。整改过程中继续保持模块化单体，不引入微服务拆分。

### 1.1 当前基线

- `go test ./...` 全部通过，`internal/handler` 测试约 40 秒。
- `go test ./... -cover` 中，`handler` 覆盖率为 77.0%，`service` 为 16.6%，`repository` 为 11.6%；`middleware`、`signing`、`storage` 没有独立测试。
- `go vet ./...` 当前失败：`FolderArchive.WriteTo(io.Writer) error` 与标准 `io.WriterTo` 方法签名约定冲突。
- 写请求通过进程级互斥锁串行化，并在每次保存文件后递归扫描整个存储根目录。
- 批量上传和站点发布在数据库事务内部执行文件读取、写入和配额扫描。
- 限流器按任意 `Authorization` 请求头创建独立令牌桶，缓存没有容量上限和过期淘汰。
- 启动过程建立多套数据库连接，真正承载 GORM 查询的连接池没有复用现有连接池配置。
- 代码中有 25 个唯一 HTTP 路径，OpenAPI 只记录 15 个。

## 2. 整改目标

### 2.1 必须达到的目标

1. 上传请求的配额判断不再递归扫描存储目录，写入复杂度不随历史文件数量线性增长。
2. 文件流式读写不再发生在数据库事务中，批量元数据写入使用固定大小的批处理。
3. 配额预留、提交和释放由 MySQL 原子协调，至少能够支持多个后端实例共享同一套元数据和 Blob 存储。
4. 文件删除失败不能形成不可追踪的孤儿文件，必须进入可重试的清理队列。
5. 限流不能通过构造不同的无效 Token 绕过，限流状态必须有容量上限和过期淘汰。
6. 数据库只保留一套受控连接池；dirty migration 必须失败并等待人工处理，不能自动 `Force`。
7. 性能、配额、清理积压和限流状态具备可验证的指标或结构化日志。
8. 保持现有 HTTP 路径、请求体、响应体、错误码和签名下载合同不变，除非单独批准破坏性 API 调整。

### 2.2 非目标

- 不把当前后端拆成微服务。
- 不在本轮实现完整 S3 兼容 API。
- 不为了形式上的解耦一次性接口化所有 repository 和 service。
- 不顺带重写前端上传流程。
- 不恢复或正式启用当前未接入运行时的分片上传会话功能；该能力另行立项。

## 3. 目标架构

```text
HTTP / Gin
  -> 请求级粗粒度限流（IP，有界缓存）
  -> 鉴权
  -> 身份级限流（已验证 scope，可选共享后端）
  -> Handler
  -> Application Service
       -> Upload Coordinator
            1. 流式写入 staging blob，并分段预留配额
            2. 以幂等方式将 staging blob 提升为最终 blob
            3. 在短事务中批量发布对象元数据和配额
            4. 将旧 blob 加入持久化清理队列
       -> Repository -> 单一 GORM/sql.DB 连接池 -> MySQL
       -> BlobStore -> LocalStorage / 共享 Blob 存储
       -> Cleanup Worker -> 重试删除和配额回收
```

继续以 MySQL 保存控制面和元数据，以 BlobStore 保存对象内容。MySQL 负责配额并发控制、Blob 生命周期和清理任务状态；文件系统扫描只允许出现在启动校验、管理命令或离线对账中，不允许进入普通请求写路径。

## 4. 优先级

| 优先级 | 工作项 | 当前风险 | 完成条件 |
|---|---|---|---|
| P0 | 持久化 Blob 台账与原子配额预留 | 每文件全目录扫描，写入近似 O(n²)，进程锁无法跨实例 | 普通写请求不调用 `directorySize`；配额可由多个实例原子协调 |
| P0 | 上传流水线与短事务 | 文件 I/O 位于数据库事务内，批量上传形成长事务 | 事务内无文件复制；元数据按固定批次写入 |
| P0 | 有界且不可绕过的限流 | 无效 Token 可创建无限令牌桶并绕过限制 | 无效 Token 按 IP 限流；缓存支持 TTL、容量上限和淘汰 |
| P0 | 性能基线与回归门禁 | 当前没有可重复的写入性能基线 | 建立单文件、100/1000 文件批量上传基准并记录查询数和扫描次数 |
| P1 | 单一数据库连接池与迁移安全 | 多连接池配置失真；dirty migration 自动强制通过 | GORM 复用受控 `sql.DB`；dirty 状态启动失败；迁移具备互斥 |
| P1 | 持久化清理任务与对账 | 删除失败只写 warning，孤儿文件不可恢复追踪 | 删除失败进入队列；支持重试、积压指标和离线对账 |
| P1 | BlobStore 边界和共享存储适配 | service 依赖具体 LocalStorage，后端只能单实例访问本地卷 | 保留 LocalStorage，并能替换为共享存储实现 |
| P1 | 可观测性 | 500 错误根因、事务耗时和清理积压不可见 | 集中记录内部错误和关键性能指标 |
| P2 | 测试分层、OpenAPI 和模块拆分 | 集成测试反馈慢，接口文档漂移，大文件持续增长 | MySQL 集成测试和静态检查进入门禁；OpenAPI 与路由一致 |

## 5. 分阶段实施

### 阶段 0：建立基线和质量门禁（P0）

目的：在改变写入模型前获得可复现证据，避免只凭单次耗时判断优化效果。

任务：

- 新增单对象上传、覆盖上传、100 文件批量上传和 1000 文件批量上传 benchmark。
- 测试数据分别预置 100、10,000 和 100,000 条对象元数据，观察历史规模对单次写入的影响。
- 记录以下数据：总耗时、每文件耗时、数据库查询数、数据库事务持续时间、目录扫描次数、写入字节数和失败清理数。
- 给 `directorySize` 增加测试计数或可替换探针，明确证明普通写请求当前会触发扫描，整改后为零。
- 修复 `go vet` 的 `WriteTo` 命名冲突，使 `go vet ./...` 可以作为后续阶段的固定门禁。
- 不批量统一现有文件换行符；只检查本阶段触及的文件。

验收：

- 基准命令、测试数据规模、机器环境和结果写入同一份性能基线记录。
- `go test ./...`、`go vet ./...` 和 `git diff --check` 通过。
- 数字性能阈值在基线完成后冻结；在此之前，后续阶段至少必须满足第 8 节的结构性指标。

### 阶段 1：持久化 Blob 台账与原子配额（P0）

目的：移除写路径中的全目录扫描和进程级全局写锁，并使配额控制具备跨实例一致性。

建议数据模型：

- 新增 `storage_blobs`：记录受管路径、大小、引用数、状态、创建时间和更新时间；受管路径必须唯一。
- 为 `system_storage_quotas` 增加 `used_bytes` 和 `reserved_bytes`。
- 新增 `storage_cleanup_jobs`：记录待删除路径、重试次数、下次重试时间和最后错误。
- Blob 状态至少区分 `staging`、`active`、`pending_delete`、`orphaned`；不要把进程内状态作为事实来源。

建议写入协议：

1. 在开始流式写入前生成最终受管路径和 staging 记录。
2. 按固定块增长 `reserved_bytes`，使用带上限条件的原子 `UPDATE`；配额不足时立即终止写入、删除临时文件并释放预留。
3. 文件写完后，以幂等方式把 staging 文件提升到最终受管路径；最终路径必须在元数据发布前可读。
4. 在一个短事务中写入对象元数据，将 reservation 转为 used，并把被替换且引用数降为零的旧 Blob 标记为 `pending_delete`。
5. 若第 4 步失败，已经提升的 Blob 仍由 staging 记录追踪，恢复任务负责删除并释放 reservation，不能留下无台账文件。
6. 事务提交后执行旧文件清理；失败时保留清理任务，由 worker 重试，实际删除成功后才从 `used_bytes` 扣除旧 Blob 大小。
7. 请求取消、进程崩溃或超时留下的 staging 记录由恢复任务按 TTL 释放。

迁移策略：

- 使用下一顺序迁移创建台账和计数字段。
- 从 `objects` 与 `recycle_bin_objects` 按 `storage_path` 汇总现有受管 Blob，避免同一路径重复计数。
- 首次迁移后必须运行一次文件系统对账：数据库未引用的物理文件登记为 `orphaned` 并计入 `used_bytes`，不能因为尚未决定是否删除就绕过物理配额。
- 对账只登记和报告 orphan，不自动删除；确认后通过清理任务逐步回收。
- 台账对账完成前不得切换新写路径；需要保存明确的 reconciliation 完成标记，避免部分扫描结果被当成完整台账。
- 新版本启动时校验 `reserved_bytes` 和过期 staging，禁止静默重置仍可能由其他实例占用的 reservation。

验收：

- 上传、覆盖、文件夹 marker、批量上传和站点发布的普通请求路径不再调用 `directorySize`。
- 同时发起的写请求不再由进程级全局 mutex 串行化。
- 两个服务实例并发写入时，`used_bytes + reserved_bytes` 不超过 `max_bytes`。
- 注入数据库失败、文件写失败和请求取消后，不留下无法追踪的配额或文件状态。

### 阶段 2：重构上传和站点发布流水线（P0）

目的：把慢文件 I/O 移出数据库事务，并减少批量请求的 SQL 往返。

任务：

- 先迁移单文件上传和覆盖，再迁移文件夹 marker、批量上传、站点文件发布和站点批量发布。
- 所有输入先完成校验和 staging；数据库事务只负责锁定必要行、批量写元数据、转换 Blob 状态和提交配额。
- 使用固定批次批量查询已有对象、批量 upsert 元数据，避免每个文件一次查询和一次写入。
- 保留当前批量操作的原子语义：任一条目失败时，本批次元数据不提交，已 staging 的文件进入统一补偿流程。
- 对超大 manifest 设置明确且已文档化的上限；上限调整必须与 `MaxUploadSizeBytes`、SQL 参数量和内存占用一起评估。
- 下载和 ZIP 继续流式返回，禁止把完整对象或压缩包读入内存。

验收：

- 数据库事务代码路径中不存在 `io.Copy`、文件打开、文件重命名或目录遍历。
- 1000 文件批量上传的 SQL 次数按批次增长，而不是每文件线性往返。
- 在阶段 0 的同一环境下，1000 个小文件场景总耗时至少下降 70%；若未达到，需要用 profile 说明剩余瓶颈并重新定标。
- 随已有对象数量从 100 增长到 100,000，单对象上传 p95 增幅不超过 20%，不计首次冷缓存。

### 阶段 3：限流可用性整改（P0）

目的：消除限流绕过和无界内存增长，并为多实例限流留出清晰边界。

任务：

- 在鉴权前只按可信客户端 IP 做粗粒度限流，不能使用尚未验证的 Authorization 值作为身份。
- 鉴权成功后由 TokenValidator 写入不可逆的 token scope，再进行身份级限流。
- 本地 limiter 缓存增加 TTL、最大条目数、定期淘汰和容量指标。
- 明确可信代理配置；只有来自网关的转发头才能影响客户端 IP。
- 保持单实例部署时使用本地 limiter；需要多实例统一总额度时，再接入共享限流后端。共享实现应隐藏在小型 store 接口后，不让 Gin handler 直接依赖 Redis 客户端。
- 为公开下载、签名下载、管理 API 和上传 API分别确定限流预算，避免大文件上传与健康检查争用同一个桶。

验收：

- 连续使用不同无效 Token 不会获得新的身份级令牌桶。
- limiter 条目数稳定在配置上限以内，过期条目可观测地被淘汰。
- 在启用共享限流后，增加服务副本不会线性放大允许的总请求速率。

### 阶段 4：数据库连接与迁移安全（P1）

任务：

- 创建一套 `sql.DB`，设置最大连接数、空闲连接数和连接最大生命周期，再通过 GORM MySQL dialector 的 `Conn` 复用该连接池。
- migration 使用明确生命周期的连接；完成后不保留无用途的 bootstrap/runtime 连接。
- 删除 handler 中未使用的 raw DB 和 GORM 字段。
- dirty migration 必须 fail fast，日志输出版本和人工恢复指引，禁止自动 `Force`。
- 多实例启动前增加迁移互斥：优先使用独立 migrate 命令或部署 job；轻量 Compose 模式可使用 MySQL advisory lock。
- 补充连接池指标：open、in-use、idle、wait count 和 wait duration。

验收：

- 业务查询和健康检查使用同一套已配置连接池。
- 并发启动两个实例时只有一个执行迁移，其余实例等待或安全退出。
- 人工制造 dirty 状态后，服务不会自动越过失败迁移。

### 阶段 5：BlobStore 与多实例运行（P1）

任务：

- 由调用方定义最小 BlobStore 接口，覆盖 staging、commit、open、delete 和 stat；不要把 LocalStorage 的全部方法原样暴露成大接口。
- LocalStorage 继续作为默认实现，并补齐独立单元测试、故障注入和路径安全测试。
- 将共享 Blob 存储适配作为单独交付，不改变现有对象 API；可以选择共享文件卷或对象存储客户端，但必须支持幂等写入和删除。
- 清理 worker 使用数据库抢占任务，支持 lease、超时接管、指数退避和幂等删除，避免多实例重复处理造成错误。
- 在没有共享 BlobStore 和共享限流之前，部署文档必须明确后端副本数只能为 1。

验收：

- service 测试可以使用故障注入的 fake BlobStore 验证写入、提交和删除失败。
- 两个实例连接同一 MySQL 和共享 BlobStore 时，可交叉上传、读取、覆盖和清理对象。
- 任意实例在 staging 或清理过程中退出后，其他实例能够接管并恢复。

### 阶段 6：可观测性、合同和代码边界（P1/P2）

任务：

- 在统一错误出口记录内部错误原因、`request_id`、稳定错误码和请求路径；用户响应继续隐藏内部细节。
- 增加上传时长/字节数、reservation 失败、清理积压、限流命中/淘汰、事务时长和数据库连接池指标。
- 健康检查改为轻量数据库 ping，并区分 liveness 与 readiness；readiness 检查数据库、BlobStore 和迁移状态。
- 将 `router.go` 按 Bucket/Object、Explorer/Recycle、Site、System 拆分注册函数和 handler 文件，但不改变路由合同。
- 清理或正式隔离未接入运行时的 upload session model、repository、migration 和配置，避免继续形成双重上传架构。
- 补齐 OpenAPI 当前缺失的 10 个路径，并增加“代码路由与 OpenAPI 路径一致”的测试。
- 增加真实 MySQL 集成测试，SQLite 继续用于快速测试，但不再作为事务、锁和迁移行为的唯一证据。

当前状态（2026-08-25）：以上代码边界任务已落地。handler、Explorer/Recycle、Blob 生命周期和 Blob 仓储已按领域职责拆分；`000012_remove_legacy_schema` 删除未接入运行时的上传会话表和 `objects.is_deleted`，公开兼容健康路由及旧 `tmp/` 扫描也已移除。

验收：

- 任一 500 响应都能通过 `request_id` 定位到保留原始 cause 的结构化日志。
- OpenAPI 唯一路径集合与 Gin 注册路由一致。
- CI 至少执行 `go test ./...`、`go test -race ./...`、`go vet ./...`、格式检查、MySQL migration up/down/up 和关键 MySQL 集成测试。

## 6. 建议 PR 拆分顺序

每个 PR 必须可独立验证和回滚，不在同一个 PR 中同时迁移所有写入场景。

1. 性能基线、测试探针和 `go vet` 基线修复。
2. 限流 key 修复、有界缓存和相关中间件测试。
3. 单一数据库连接池、dirty migration fail-fast 和迁移互斥。
4. `storage_blobs`、配额计数和清理任务 schema/repository，不切换业务流量。
5. 单对象上传切换到 reservation + staging 流水线。
6. 覆盖上传、删除、回收站和 bucket 删除接入 Blob 生命周期。
7. 批量上传和站点发布移除事务内文件 I/O，并改成批量 SQL。
8. 清理 worker、staging 恢复和对账命令。
9. BlobStore 边界与共享存储适配；完成双实例验证。
10. 集中错误日志、指标、OpenAPI 同步和 handler 拆分。

依赖关系：第 4 项是第 5 至第 9 项的基础；第 5 项验证稳定后才能迁移其他写入链路；共享存储上线前必须先完成配额跨实例协调和清理任务租约。

## 7. 兼容与回滚策略

- schema 先行、代码后切换：新增表和字段必须允许旧版本继续读取原有表。
- 切换写路径前，先以只读方式对比目录扫描结果和 Blob 台账结果；出现差异只报警，不自动删除文件。
- 单对象上传、批量上传和站点发布分别切换，不能一次性替换全部入口。
- 新写路径发生异常时，允许回滚到旧版本；回滚前必须确认没有未处理的 staging reservation，并保留对账命令。
- 清理任务必须幂等。删除不存在的物理文件应视为成功，但必须验证没有活跃对象引用该路径。
- 数据库 migration 不允许应用进程自动降级；回滚 SQL 只在确认数据兼容后人工执行。

## 8. 统一验收指标

### 8.1 结构性指标

- 普通写请求中的目录扫描次数：`0`。
- 数据库事务内的文件系统读写次数：`0`。
- 进程级全局上传 mutex：移除。
- limiter 条目数：不超过配置上限。
- 无持久化记录的删除失败：`0`。
- GORM 业务连接池数量：`1`。
- 自动强制通过 dirty migration：`0`。

### 8.2 性能指标

- 1000 个小文件批量上传较当前基线总耗时下降至少 70%。
- 已有对象从 100 增长到 100,000 时，单对象上传 p95 增幅不超过 20%。
- 批量元数据 SQL 次数按固定 batch size 增长，不允许每文件独立查询和独立 upsert。
- 性能测试必须同时记录 CPU、内存峰值、数据库连接等待和临时磁盘峰值，不能只记录 HTTP 总耗时。

### 8.3 一致性指标

- `used_bytes` 等于 active、recycle、pending_delete 和 orphaned 受管 Blob 的物理占用总和。
- `reserved_bytes` 只包含有效 staging；过期 reservation 能被安全恢复。
- 数据库中 active 对象引用但物理文件缺失的数量为 0。
- 无数据库记录且超过安全 TTL 的受管文件数量为 0。

## 9. 完成定义
