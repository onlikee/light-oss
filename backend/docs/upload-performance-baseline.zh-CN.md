## 2. 测试参数与口径

- 上传内容固定为 1 KiB；历史对象分别预置 100、10,000 和 100,000 条，每条历史对象对应 64 B 文件记录。
- 场景包括单对象新建、单对象覆盖、100 文件批量上传和 1000 文件批量上传。
- 整改前批量基准在基线提交的临时隔离工作树中加入同口径探针。旧路径将连接池设为 2；设为 1 会因旧架构的嵌套连接获取而死锁，因而没有用更小连接池人为拖慢旧基线。
- 独立样本使用 `-benchtime=1x -count=5` 并取 `ns/op` 中位数。稳态 p50/p95 使用 `-benchtime=5x`，基准内部排除第一个冷缓存请求。
- MySQL 历史规模门禁同时创建 100 与 100,000 条历史记录的隔离数据库，分别预热 5 次，并在同一轮中交替执行 100 次上传，抵消顺序执行时 redo、fsync、后台刷盘和主机负载漂移。样本数达到 20 后，p95 增幅超过 20% 会直接使 benchmark 失败。
- `queries/op` 是数据库驱动层调用数；`transaction_ns/op` 是事务区间累计时间；`directory_scans/op` 是普通写路径调用全目录容量扫描的次数。

## 3. 可重复命令

在 `backend` 目录执行：

```powershell
go test ./internal/service -run '^$' -bench '^BenchmarkObjectUploadCurrentPath$/^history_(100|10000|100000)$/^(single|overwrite)$' -benchtime=1x -count=5 -benchmem -timeout=20m
go test ./internal/service -run '^$' -bench '^BenchmarkObjectUploadCurrentPath$/^history_(100|10000|100000)$/^batch_(100|1000)$' -benchtime=5x -count=1 -benchmem -timeout=20m
go test ./internal/service -run '^$' -bench '^BenchmarkObjectUploadCurrentPath$/^history_100$/^batch_(100|1000)$' -benchtime=1x -count=5 -benchmem -timeout=10m
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\measure-upload-benchmark.ps1

$env:MYSQL_TEST_DSN = '<具备 CREATE/DROP DATABASE 权限的 MySQL DSN>'
go test ./integration -run '^$' -bench '^BenchmarkMySQLObjectUploadLatency$' -benchtime=100x -count=1 -benchmem -v -timeout=30m
Remove-Item Env:MYSQL_TEST_DSN
```

整改前隔离工作树使用的命令为：

```powershell
go test ./internal/service -run '^$' -bench '^BenchmarkObjectUploadOldBatchPath$/^history_100$/^(batch_100|batch_1000)$' -benchtime=1x -count=5 -benchmem -timeout=15m
```

该 `OldBatchPath` 探针仅用于基线提交的临时工作树，不属于整改后产品代码。

## 4. 真实旧路径与最终批量路径对比

两侧均为 `history_100`、五个独立样本的中位数：

| 场景 | 整改前样本 | 整改前中位数 | 整改前扫描 | 整改后中位数 | 整改后 SQL / 事务 / 扫描 | 总耗时下降 |
|---|---|---:|---:|---:|---:|---:|
| 批量 100 | 881.046 / 803.366 / 793.425 / 1051.850 / 1118.578 ms | 881.046 ms | 100 | 84.206 ms | 11 / 2 / 0 | 90.44% |
| 批量 1000 | 48.796 / 54.024 / 48.839 / 53.146 / 53.864 s | 53.146 s | 1000 | 810.334 ms | 76 / 2 / 0 | 98.48% |

整改后五次 `batch_100` 为 90.312、84.206、82.469、104.413 和 77.825 ms；五次 `batch_1000` 为 810.334、760.643、821.120、853.564 和 796.205 ms。两组均为 0 次目录扫描、0 次连接池等待和 0 次失败清理。

旧路径每写一个文件都会重新扫描整个存储根目录，批量场景分别产生 100 和 1000 次扫描，因此随文件数和已有文件数近似 O(n²)。最终路径使用持久化 Blob 台账、一次总配额预留、固定批次 SQL 和最多 16 个 staging worker；1000 文件门禁要求下降至少 70%，实测下降 98.48%。

## 5. 整改后本地基准

每个场景连续执行 5 次，p50/p95 排除第一个冷缓存请求：

| 场景 | 平均总耗时 | p50 | p95 | SQL/请求 | 事务/请求 | 事务累计时间/请求 | 扫描 | DB 等待 | 写入字节 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 单对象 | 3.568 ms | 3.173 ms | 4.855 ms | 11 | 3 | 0.517 ms | 0 | 0 | 1,024 |
| 覆盖 | 3.956 ms | 3.552 ms | 4.655 ms | 15 | 3 | 0.814 ms | 0 | 0 | 1,024 |
| 批量 100 | 79.657 ms | 71.566 ms | 92.181 ms | 11 | 2 | 6.586 ms | 0 | 0 | 102,400 |
| 批量 1000 | 968.470 ms | 922.820 ms | 1,135.357 ms | 76 | 2 | 87.544 ms | 0 | 0 | 1,024,000 |

批量 SQL 上界为固定批次函数，而不是每文件独立往返：100 文件为 11 条，1000 文件为 76 条。benchmark 会对总 SQL、Blob SQL、事务数和零目录扫描执行硬断言。

|---:|---:|---:|---:|---:|---:|---:|---:|

| 10,000 | 3.998 ms | 5.046 ms | 86.634 ms | 917.929 ms | 11 / 15 | 11 / 76 | 0 |
| 100,000 | 5.113 ms | 5.678 ms | 87.078 ms | 914.077 ms | 11 / 15 | 11 / 76 | 0 |

SQLite 数据用于证明查询数、事务数和扫描次数不随历史对象数增长；正式 20% p95 门禁以下面的真实 MySQL 配对结果为准。

## 6. MySQL p95 历史规模门禁

最终 100 样本配对结果：

| 历史对象数 | p50 | p95 | SQL/上传 | 连接等待/上传 |
|---:|---:|---:|---:|---:|
| 100 | 17.919 ms | 31.708 ms | 11 | 0 |
| 100,000 | 18.091 ms | 32.928 ms | 11 | 0 |

p95 增幅为 `3.845%`，低于 `20%` 门禁并由 benchmark 硬断言。点查执行计划分别命中 `udx_objects_bucket_key` 和 `storage_blobs.PRIMARY`，没有全表扫描。

早期按“小表子基准完成后再播种并执行大表子基准”的顺序测量曾得到 68.29% 的不稳定增幅；当时查询数仍为 11、连接池等待仍为 0。该结果受 100,000 行播种后的 MySQL redo/fsync 与后台刷盘偏置，不能作为历史规模退化结论，因此最终门禁改用交替配对采样。

## 7. CPU、内存与临时磁盘峰值

`measure-upload-benchmark.ps1` 以 100 ms 间隔采样最终 `history_100/batch_1000` 单次请求：

| 总耗时 | CPU 峰值 | 工作集峰值 | 临时磁盘峰值 | DB 等待 | SQL / 事务 / 扫描 |
|---:|---:|---:|---:|---:|---:|
| 1,032.429 ms | 15.05% | 27,107,328 B | 443,712 B | 0 | 76 / 2 / 0 |

峰值属于单次操作系统采样，不作为稳定延迟门禁；脚本会验证测试进程退出码并清理其专用临时目录。

## 8. 验收结论

- 1000 个小文件批量上传相对真实旧路径中位数下降 98.48%，通过至少 70% 的数字门禁。
- MySQL 中已有对象从 100 增长到 100,000 时，单对象上传 p95 增幅 3.845%，通过不超过 20% 的数字门禁。
- 普通上传、覆盖和批量上传均为 0 次目录扫描；查询数和事务数不随历史对象总量增长。
- 100/1000 文件批量写入分别固定为 11/76 条 SQL、2 个事务；文件 I/O 不在数据库事务内。
- 基准同时记录了端到端耗时、每文件耗时、SQL、事务时间、扫描、写入字节、失败清理、连接等待及系统峰值，满足整改计划的性能证据要求。
